# 10/19 실제 클립 웹 증거 수집 안내

이 폴더는 **수집 절차와 빈 양식**이다. 실제 연속 촬영·음성·학생 설명을 완료했다고 주장하지 않는다.
소스는 React 웹이며 Flutter 앱을 자동 변환한 것이 아니다.

## 1. 맥에서 수정본 적용

먼저 맥을 인터넷 가능한 Wi-Fi(WMS 등)에 연결해 수정본을 받는다. ClipSense 복구 Wi-Fi는 인터넷이 없어 Git 다운로드가 안 될 수 있다.
웹 서버 터미널에서 Control+C 후 저장소 루트에서 한 줄씩 실행한다.
실패하면 다음 명령을 실행하지 않는다. 로컬 변경을 reset/삭제하지 않는다.

```bash
cd ~/2026-ClipSense-CloseYourMouthandeatBread
git fetch https://github.com/paulschoolwms-hue/2026-ClipSense-CloseYourMouthandeatBread.git codex/esp32-camera-web
git merge --ff-only FETCH_HEAD
cd web
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

의존성이 없는 경우에만 `npm ci --cache "$HOME/.npm-clipsense-cache"`를 먼저 실행한다.
Local 주소를 맥 브라우저에서 연다. 서버 터미널은 계속 켜 둔다.
기존 화면이 남으면 새로고침하고 증거 수집 패널의 **코드 버전**을 확인한다.
새 포트로 임의 변경하지 말고 5173을 사용 중인 자신이 실행한 기존 서버를 종료한다.

## 2. 연결 조건 고정

경로: 맥 브라우저 HTTPS localhost → 같은 맥의 Vite 중계 → ESP32 HTTP `/capture`.
브라우저는 ESP32 HTTP를 직접 fetch하지 않는다. CORS/mixed-content/인증서 보호를 끄지 않는다.
수정본을 받은 후에만 필요에 따라 맥을 ClipSense 복구 Wi-Fi로 전환한다. 로컬 웹 서버는 계속 실행해 둔다.
토큰은 웹 비밀번호 칸에서 메모리에만 보관하고 기기 요청 헤더로 전달한다.
비밀번호·토큰·secrets.h를 결과 파일이나 영상에 포함하지 않는다.
GitHub Pages는 이 중계 서버를 실행하지 못하므로 실제 클립 검증은 맥 로컬 서버에서 한다.

- **WMS 등 공유기 Wi-Fi**: 맥과 ESP32가 같은 내부망. 주소는 보드 부팅 로그의 `ip`를 쓴다.
- **복구 Wi-Fi ClipSense-***: 맥을 그 Wi-Fi에 연결하고 인터넷 없음 상태를 유지한다.
  주소는 보통 `http://192.168.4.1`이며 로그 `ip`로 확인한다.
  Wi-Fi 비밀번호는 `CLIP_AP_PASSWORD`, 기기 토큰은 `CLIP_DEVICE_TOKEN`으로 서로 다르다.
- 맥 주소(예: 192.168.0.73)를 기기 주소로 입력하지 않는다. ESP32 주소는 `http://`이다.
- 연결 실패 시 새 터미널에서 저장소 루트의 `bash scripts/diagnose_clip_mac.sh`를 실행한다.
  두 후보 IP와 실제 부팅 로그 IP가 다르면 로그의 IP를 별도로 검사한다.
- `/health`의 무인증 401은 네트워크 성공이다. 000/시간 초과는 연결 문제, 403은 인증 확인이 필요하다.
- 새 펌웨어 업로드는 이번 웹 증거 기능에 필요하지 않다. 기존 0.3.0/0.3.1 프로토콜을 지원한다.

## 3. 과제 1 — 연속 갱신 증거

1. `ESP32 카메라로 신호등 인식 시작` → 주소/토큰 입력 → `ESP32 연결`.
2. `새 사진 수신 중`, 실제 센서(OV3660 등), 기기 프레임 번호, 마지막 성공 수신 시각을 확인한다.
3. 카메라 앞에서 손·물체를 움직이고 30초 이상 사진이 계속 바뀌는 장면을 촬영한다.
   사진, 성공 횟수, 프레임 번호가 함께 보이게 한다.
4. `현재 원본 JPEG 저장`으로 원본 예시를 보관한다.
5. 잠시 ESP32 연결을 끊어 마지막 성공 시각/횟수가 늘지 않고 대기로 전환되는지 촬영한다.
   `연결 장애 장면 기록` 후 다시 연결한다. 실패 화면 뒤 남은 정지 사진은 실시간 영상 증거가 아니다.

## 4. 과제 2 — 정답/판독/최종 안내를 분리

규칙은 `hsv-components-v2`. 전체 정의와 임계값은 세션 JSON의 `detector`에 저장된다.

- 원본을 320px로 축소한 뒤 상단 60%에서 HSV 색 마스크를 만든다.
- 빨강 hue ≤20 또는 ≥340, 초록 100~200, saturation>0.35, brightness>0.35.
- 4방향 연결 영역의 최소 면적(ROI 0.3%·샘플 5개), 최대 면적(35%),
  종횡비(0.15~2.5), 채움(15% 이상)으로 단순 공간 후보를 검사한다.
- 두 색 후보가 함께 있으면 불명. 흩어진 잡음·큰 색 면·가는 선을 제외한다.
- 학습 AI, 보행자 모양 분류, 실제 도로 정확도 측정이 아니다. 색 물체를 신호로 오인할 수 있다.
- 연결 영역 크기·모양 검사는 단순 검사이며 Dart/Python의 전체 비전 파이프라인을 이식한 것이 아니다.
- 실제 카메라 모드에는 C-ITS 모의 응답을 주입하지 않는다.
  **실제 신호/남은 시간이 없으므로 초록 후보여도 최종은 항상 WAIT(대기)**.
  원본 `SCENARIO` 모드는 MOCK으로 따로 표시하며 실측 증거로 제출하지 않는다.

빨강/초록/신호 없음 장면을 각각 3회 권장한다. 테스트 사진을 화면에 띄우거나 인쇄해 썼다면
`장면 종류`에 그 방법을 정확히 선택한다. 실제 신호등 실측이라고 쓰지 않는다.
각 장면에서 정답을 직접 선택하고 화면 판독·최종 대기를 확인한 뒤 `현재 장면 기록`을 누른다.
잘못 판독한 결과도 삭제하거나 성공으로 바꾸지 말고 그대로 기록한다.
사진과 판독 프레임이 일치하지 않거나 사진이 오래되면 기록이 거부된다.

다림/폴이 각자 설명할 내용:
1. ESP32 촬영 → 인증 JPEG → 맥 중계 → 브라우저 분석 → 최종 대기 → 음성.
2. 색상 후보와 보행 가능 판정은 다르다.
3. 초록이어도 실제 남은 시간·실시간 신호 정보가 없으면 대기한다.
4. 연결 실패·정지·재전송은 새 성공 프레임이 아니다.

## 5. 과제 3 — 소리를 직접 확인

1. 맥 스피커 음량·출력 장치를 확인하고 `음성 시작 (현재 안내 읽기)`를 직접 누른다.
2. 빨강/초록/신호 없음 장면을 바꿔 각 안내를 듣는다. 필요하면 `현재 안내 다시 듣기`를 누른다.
3. `이번 안내 직접 청취`를 들림/안 들림으로 직접 선택하고 해당 장면을 기록한다.
   기본값 미확인은 실패나 성공으로 자동 변환되지 않는다.
4. 휴대폰 등으로 맥 화면과 실제 스피커 소리를 함께 촬영한다.
   재생해서 소리가 실제로 녹음됐는지 확인한다. 화면 문구만으로 완료 처리하지 않는다.
5. 세션 JSON/CSV를 먼저 저장한다. ESP32 전원을 껐다 켜고 현재 Wi-Fi/기기 IP를 다시 확인한 뒤, 브라우저를 새로 열고 다시 연결·음성 시작을 수행한다.
   재실행 영상을 별도로 남긴다. 이전 기록은 탭 메모리에만 있으므로 재시작 전에 저장한다.

음성 이벤트 requested/started/ended는 브라우저 API 이벤트일 뿐 실제 청취 증거가 아니다.
실제로 들리지 않으면 `안 들림`과 오류를 기록한다. 오프라인 한국어 음성이 없는 브라우저/OS에서는
미리 음성을 설치하거나 지원 브라우저로 변경하고 변경한 조건을 기록해야 한다.

## 맥에서 localhost 인증서 경고가 나타날 때

브라우저 경고를 무시하거나 TLS/보호 기능을 끄지 않는다. 서버를 Control+C로 종료하고
`web/`에서 로컬 전용 HTTP 옵션을 사용한다.

```bash
CLIPSENSE_HTTP_LOCAL=1 npm run dev -- --port 5173 --strictPort
```

브라우저에는 `http://localhost:5173`을 입력한다(https가 아님).
이 옵션은 서버를 127.0.0.1에만 바인딩한다. 브라우저는 HTTP localhost를 신뢰할 수 있는
로컬 출처로 취급한다. 다른 기기의 IP나 외부 서버에는 이 방법을 적용하지 않는다.
ESP32 주소는 계속 `http://<보드 IP>`이며 요청은 같은 맥의 중계를 거친다.
제출 조건에는 실제 사용한 HTTP localhost 주소를 기록한다.

## 웹 서버와 ESP32는 응답하는데 화면에서 연결 실패일 때 (10/22)

맥 localhost의 HTTP 200과 ESP32 `/health`의 401은 각 서버까지의 접속 성공이다.
이 두 결과만으로 브라우저 요청, 맥의 ESP32 중계, 인증된 사진 수신이 성공했다고 판단하지 않는다.
브라우저의 AbortSignal.any/timeout 미지원도 과거에는 서버 오류로 잘못 표시됐다.
수정본은 이 API 없이 시간 제한·취소를 유지하고 요청/본문 수신/해석 단계를 구분한다.
브라우저 보호 기능이나 2초 신선도 기준을 끄지 않는다.

중계 경로도 무인증으로 검사할 수 있다(웹 포트/기기 IP는 실제 값으로 바꾼다).

```bash
curl --max-time 7 'http://127.0.0.1:5174/esp32-proxy?url=http%3A%2F%2F192.168.0.54%2Fhealth'
```

`missing_device_token`이면 중계까지 응답한다. 이는 사진 촬영 성공을 뜻하지 않는다.
이후 토큰을 웹 입력칸에서 입력하고 사진 수신 결과를 확인한다.
브라우저 자동 검사는 Chromium에서 최신 시간 제한 API를 제거한 환경으로도 수행하며,
실제 Safari 버전·맥 권한·기기 네트워크 검증은 별도로 필요하다.

## ESP32 영상 180도 회전

웹의 ESP32 미리보기와 분석용 픽셀을 함께 180도 회전한다. 분석 영역은 회전된 화면의 상단 60%이다.
텍스트/오류/분석 영역 표시는 회전하지 않는다. 내장 카메라에는 적용하지 않는다.
기기 펌웨어는 변경하지 않는다. `현재 원본 JPEG 저장`은 전송받은 회전 전 원본을 보존한다.
세션 JSON의 장면 기기 정보 `rotationDeg: 180`이 웹 표시/분석 방향을 기록한다.
